وفق التوجيه الرئيسي (Master Directive): Discovery أولًا، ثم خطط، ثم تنفيذ مرحلة‑بمرحلة
`PLAN → IMPLEMENT → TEST → FIX → VERIFY`. هذه الوثيقة هي المرجع الحي؛ تُحدَّث مع كل مرحلة.

## 1) PROJECT AUDIT

**الهوية**: Flutter 3.35 (Dart ^3.9)، Provider + shared_preferences، عربي RTL أولًا + إنجليزي،
فاتح/داكن، Android/iOS/Web/Windows. لا Backend ولا قاعدة بيانات خادمية ولا AI — التطبيق
**Offline‑first بالكامل، البيانات على الجهاز فقط**.

| المحور | الحالة الفعلية (مُتحقَّق منها) |
|---|---|
| البنية | 10.3k سطر Dart؛ طبقات: `core/` (توطين، ثيم، إشعارات، تصدير)، `models/`، `state/` (AppState)، `screens/`، `widgets/`. الفصل جيد. أكبر الملفات: l10n 1156، app_state 1020، task_editor 958، home_tab 916. |
| التخزين | مفتاح واحد `waqti.v1` (JSON) + نسخة احتياطية يومية `waqti.backup.v1`. لا مخطط علائقي — مناسب لحجم البيانات الحالي (مئات السجلات). |

**ما يعمل**: كل الوظائف المستخدمة يوميًا (أُثبت بمسح نقر آلي على كل الأزرار).
**ما لا ينطبق حاليًا**: Backend/API/RLS/Payments/AI/Admin/Notifications server — لا وجود لها بالتصميم.
**الفجوة الوحيدة المخالفة للتوجيه (البند 45)**: شاشة «تسجيل دخول/إنشاء حساب» ببريد وكلمة مرور
بلا خادم = وظيفة شكلية. **قرار مطلوب منك** (القسم 9).

## 2) ARCHITECTURE PLAN

- الإبقاء على الطبقات الحالية؛ تقسيم الملفات > 900 سطر تدريجيًا (بلا تغيير سلوك):
  `home_tab` → `home/today_card.dart`, `home/month_grid.dart`, `home/overdue_card.dart`؛
  `task_editor_sheet` → أقسام (basics/schedule/reminders)؛ `app_state` → mixins (stats/backup/reminders).
- طبقة تخزين مجردة `StorageService` (واجهة) فوق shared_preferences لتسهيل الانتقال لاحقًا إلى Drift/SQLite
  عند تجاوز ~5k سجل، أو إلى مزامنة سحابية.
- أي مزامنة/حساب حقيقي = **Supabase** (Auth + Postgres + RLS) وفق `docs/SYNC.md` — مرحلة 13 في ROADMAP،
  لا تبدأ إلا بقرار ومشروع Supabase منك.

## 3) DATABASE PLAN

- الآن: JSON محلي بإصدار `v1` + ترحيل تلقائي للحقول القديمة (`reminder`→`reminders`). نسخة يومية + استعادة **مختبرة**.
- عند الحاجة (Drift): جداول `tasks`, `categories`, `task_days(task_id,date,status,progress,note)`, `focus_log`
  بمفاتيح أساسية/أجنبية وفهارس على `(task_id,date)`، `deleted_at` للحذف المنطقي، Migrations مرقّمة.
- سحابي (Supabase): نفس المخطط + `user_id` وسياسات RLS «المستخدم يرى صفوفه فقط» تُختبر فعليًا.

## 4) SECURITY PLAN

- ✅ لا أسرار في الكود؛ فحص آلي في CI. ✅ بيانات محلية فقط؛ لا تتبع. ✅ بيان خصوصية iOS + سياسة خصوصية.
- ✅ التحقق من المدخلات: أسماء (trim/طول)، أهداف رقمية، JSON مستورد.
- ⏳ عند إضافة خادم: HTTPS فقط، JWT قصير العمر، RLS، Rate limit، تحقق Webhook، تسجيل تدقيق للعمليات الحساسة.
- ⏳ اختياري: تشفير التخزين المحلي (SQLCipher) إن ظهرت حاجة (بيانات غير حساسة حاليًا).

## 5) AI PLAN

لا يوجد AI في المنتج حاليًا ولا في خارطة الإطلاق. إن أُضيف لاحقًا (اقتراح عادات/تلخيص أسبوع):
Frontend → Backend Gateway (مفتاح المزوّد خادميًا فقط) → Validation → Provider → Output validation.
`SOURCE_LOCK = TRUE` لأي محتوى ديني: لا توليد نصوص شرعية بلا مصدر موثّق (البنود 16–17).

## 7) DEPLOYMENT PLAN

- الويب: نشر تلقائي مع كل push (Pages). Staging = معاينة محلية + بناء PR؛ Production = الفرع الرئيسي.
- المتاجر: `release.yml` (حِزم + GitHub Release) ثم `publish.yml` (Play internal → production، TestFlight → App Store، Partner Center).
- المراقبة: Play Console (ANR/Crash) + TestFlight + GitHub Actions. لا خدمة تتبع خارجية (لا بيانات تُرسل).
- النسخ الاحتياطي: محلي يومي + تصدير JSON بيد المستخدم (لا خادم = لا بيانات لدينا نفقدها).
